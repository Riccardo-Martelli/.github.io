In my first article I wrote about learning by doing. nvimpp is that idea applied to code: a small C++ program I wrote mostly by hand, between other projects, because I still enjoy programming and because one daily annoyance had become too much.

I live in the terminal, and two tools there changed how I work. zoxide remembers the folders I visit and jumps to the right one from a few letters. atuin records my shell history and lets me search and browse it. Neither does the last step, opening the file. With zoxide I jumped to a folder, then still had to find the file and open it in Neovim (nvim). Hopping between projects like that all day was a pain.

What it does

nvimpp is a thin wrapper around Neovim. It records every file I open, then hands the arguments to Neovim untouched, so it can replace nvim without changing anything else. The useful part is one key. I type nvim main and press Alt-Enter instead of Enter, and Neovim opens the file I use most whose name contains main, wherever it is on disk. When I quit, I am back in the folder I started from. I used it to edit this website.

nvimpp: opening a file by name, and jumping to the best match with Alt-Enter.

Its companion, nvimi, is the atuin side: it reads the history and shows an inline picker of my most used files, plus statistics and the raw history. The code is on GitHub.

nvimi: the picker ranked by frecency, the statistics, and the history.

A bit of statistics, a bit of programming

Deciding which file is "the one I use most" does not need artificial intelligence (AI). It needs one formula. Each time I open a file, that launch adds 0.5^(age / half-life) to the file's score, where age is the time since the launch. With a half-life of 7 days, a launch from today counts 1, one from a week ago 0.5, one from a month ago about 0.05. Files that are opened both often and recently rank first. This is what zoxide calls frecency.

The programming was the fun part. Even a tool this small makes you deal with how the machine works underneath: how memory is managed, how to choose types so that whole families of errors cannot happen, how a program reads keys from the terminal and hands control to another process. I learned more of that writing nvimpp than I would have by reading about it.

Where AI comes in

I did not write nvimpp with AI. I used it mostly for debugging. On many platforms people complain that programming has turned into waiting for a coding agent to finish, and this project went the other way.

Still, it turned out to be useful for exactly that kind of work. People who use coding agents keep several sessions open, check what each agent changed, paste code from one to another, and review the result. Every one of those steps means reaching a file that lives somewhere else. nvimpp makes that jump quick from wherever you are.

I think there is something poetic in writing code that AI cannot replace, but AI is a good tool to work with. It can make code more robust and it helps when something breaks. Mostly it works as a quicker Stack Overflow: it points you to a function, or explains how a system you don't know behaves. After that the work is yours. You read the function, understand it, and use it again later on your own, or the code stops working and you won't know why. You iterate many times before it works.

nvimpp was not meant to work with AI. It was a fun project that happened to be useful there too.
